IWhy long games need memory

We give a coding model a Minecraft world and nothing else. It sees the world only as first-person frames and plays in turns: each turn it looks at the newest frame and writes a short list of actions, which the environment then executes. In the Ender Dragon task it has a budget of 36,000 steps, about half an hour of game time, to work through 24 milestones, from the first log to the dragon. Most of what makes this hard comes down to memory.

What it needs is out of view

The agent walks past an iron vein early on and needs it thousands of steps later, long after the vein has left the screen and the model's context.

Mistakes compound

Each milestone builds on the ones before. Dying in lava loses everything it carries, and the same lake will kill again unless the agent remembers it.

Skills are learned in play

No one gives it a procedure for tunneling or for fighting a blaze. It has to notice what worked and save it in a form it can reuse, in this life and the next.

Without memory, all three models we tried stall at about six of the 24 milestones. So the question is what to keep from such a long game, and how the agent can find it again when it matters.

IIHow agents remember

Agent memory has gone through a few designs, each recovering something the one before it lost. We compare them on one question from our runs: early on, the agent walks past a shallow iron vein, and thousands of steps later it needs iron. Where was the vein?

    Multimodal filesystem memory

    MFM files each frame it records under cues and keeps what the agent learns next to it.

    each frame under when, where, whatfound by place

    KeepsThe frame, state and outcome of every action, indexed by when, where and what happened, plus the agent's own facts, procedures and plan.

    Finds things byA query on the cues, then a look at the frames.

    LosesNothing it recorded. Its notes can be wrong, so each one cites the episodes it came from.

    The iron veinAsk for the place, open the frame, set it beside the live view.

Text is easy to search but loses what things looked like; raw frames keep everything but are hard to search. In MFM we keep the frames and put a small text index on top of them, so a short query leads back to the full picture, and the agent files what it learns next to that evidence. In the next section we follow our agent back to the iron vein.

IIIHow MFM works

We store the agent's memory as plain files in its workspace, sorted into the five kinds of memory in Figure 2 of our paper. The harness, the program that runs the environment for the agent, writes two of them as the agent plays: episodic memory, one episode per action with its frame, state and outcome and a row of cues in index.jsonl; and spatial memory, a grid of where the agent has been. The agent writes the other three itself: semantic notes, procedures it can call as actions, and a working plan. It reads all five with ordinary shell commands during its turn, and the whole directory passes on to its next life.

The figure below replays about 600 steps of one run, the third life of a GPT-6-Astra chain on Ender Dragon. The agent walks back to the iron vein its first life found and mines it at step 4,231, about 1,100 steps earlier than the first life did. Every frame, command and file line in the figure comes from the run's record. Stages 1 to 4 make up one turn and repeat; stage 5 comes when a life ends. About this replay

We show the memory as the harness and the agent wrote it: the rows of index.jsonl, the map, the log, and the notes in mine/. Pause or move the step to look at any moment. A query runs over the memory as it stood then, with the rules of the agent's own tool. Everything here is the record of one run, exported by scripts/export_demo.py. Nothing is simulated and no model is called.

  • The index is a file, and the query is a filter. MFM computes no embeddings and ranks nothing. index.jsonl has one row per closed episode, and tools/episodes.py selects rows by step range, by distance from a point, by tag, by action, or by text found in the episode's files. Filters combine with AND, and results come back in the order they were recorded.
  • The query box runs a port of that tool. It was checked against this run: each episodes.py call the agent made was re-run over the index as it stood at that turn and compared, line for line, with the output the run recorded.
  • Replaying the harness's files is exact. The index, the grid and the log are append-only and every row carries its step, so the memory at step s is the rows written by step s.
  • The agent's own files are rebuilt from its patches. The run keeps only the final mine/ files. Their history here comes from the apply_patch calls in the session record, and is shown only when replaying those patches gives back the final file exactly.
  • The video is the run's own recording, one frame per step. The page takes its step from the frame on screen, so the memory on the left is always the memory at the moment the video shows.
  • Frames are reduced. The stored frames are PNG; the page shows JPEG copies no larger than 320×180. Recorded command output is cut at 6,000 characters. Reference and skill files, and images the agent made, are listed and not included.
  • The tool differs between runs. Each run carries its own copy of tools/episodes.py, and the query box accepts the flags of the copy the chosen run had. Where a run carried the memory of earlier lives, the export has the index of those lives and not their episode files, so --previous returns their rows without the harness notes.
  • One run. Each entry in the list is a single recorded life. It shows how the memory is built and read, and says nothing about how often the agent succeeds.

VResults

We compare MFM with the same agent without memory (Direct) and with two recent memory systems for long-horizon agents, PRO-LONG and VISTA, each on three models. In Minecraft (MCU-AgentBeats), Mine Diamond from Scratch has 10 milestones in a budget of 12,000 steps, and Ender Dragon has 24 milestones in 36,000 steps. In CUABench-KiCad, the agent designs and edits circuits in a desktop app through screenshots, mouse and keyboard, and each task is scored from 0 to 1. We ran every setting with three seeds; bars show the mean and whiskers one standard deviation.

MFM has the highest mean with every model on every task, and the gap is widest on Ender Dragon, the longest task. With GPT-6-Astra it reaches all 10 Mine Diamond milestones, and 15.0 of 24 on Ender Dragon, where the best baseline averages 12.7. On KiCad it averages 0.440 with GPT-6-Astra, against 0.400 for the best baseline and 0.267 without memory.

In the next two sections we look at where these gains come from: how the agent uses the frames it keeps, and what it carries over from one life to the next.

VILooking back at past frames

The index leads the agent to the right episode, but what it checks is the frame. Our agents often open past frames, from the current life and from earlier ones: episodes.py --then-now puts a past frame beside the live view, and zoom.py crops a frame for a closer look. Below, we marked five of these looks on one life's milestone staircase and show four of them larger underneath.

Most of these looks happen within a life. The same files also pass on to the next life, and that is where the agent gets better at the task itself.

VIIGetting better across lives

When a life ends, we pass its records and the agent's own files on to the next life, in the same world. The model's weights never change, so anything the next life does better comes from what it reads. We followed one chain of three lives with GPT-6-Astra; the third life is the one in the figure above and in the explorer.

Within the 36,000-step budget, life 1 started from an empty memory and reached 10 milestones. Life 2 started with life 1's 1,170 episodes and reached 15, and life 3, with 3,957 episodes from both, reached 16. The iron vein from the figure is one place where the gain shows: all three lives mined their first iron at that same block, at steps 5,325, 5,033 and 4,231. Life 3 also had its iron pickaxe at step 5,293, 950 steps before life 1, and flint and steel at step 9,995, where lives 1 and 2 needed 23,032 and 28,009.

Procedures carry over too. Of the 145 calls life 3 made to its own procedures, 98 went to two it brought over from life 2 at the start, west_level (62 calls) and west_stairs (36). Another 11 went to north_level, which it rewrote from life 2's version partway through, and the remaining 36 went to five procedures it wrote during the life.

A caveat: this is one chain in one world, so the gain mixes remembering the map with remembering what works, and the lives ran for different lengths (life 1 stopped at step 30,286; lives 2 and 3 ran longer). In other chains we ran with the released code, the score did not go up with every life (see the MFM repository README).

Each part of the memory counts

With GPT-5.6-Sol, each component is taken away in turn: the frames stored with each episode, the index (replaced by a flat, chronological search of the log), the agent's own procedures, and consolidation. Each removal costs between 1.0 and 2.4 milestones.

Building a Nether portal

A construction probe: on a cleared stone platform with enough materials, build and light a Nether portal from a text description of its shape, within 6,000 steps. The agent has to turn the description into a structure and follow its progress from first-person views. Only MFM finished the portal, and it made the fewest calls.

Fewer, longer turns

MFM and PRO-LONG run many more environment steps per model call than VISTA, which plays a few steps and looks again; over a run that means far fewer model calls.

Does a look change the plan?

How far back it looks

Skills it wrote for itself

The same files let the agent get better at a task within a life. When a sequence of actions has worked several times, it saves the sequence as a procedure under mine/procedures/ and calls it from then on. A later life inherits those procedures, repairs them, and adds its own. Because everything the agent knows beyond its weights is a file it wrote, what it learned can be checked by reading the files and the turns that wrote them.

Four operations at one real step

a

Record

The episode that ended in the death is ep_001391: the frame (a brute and a raised shield), the state (health 1.5), the plan entry, and the outcome, in which the whole kit is lost.

b

Index

The store appends one row to index.jsonl. Steps, position, tags, action kind, summary, note and events are searchable; the image and path are references that the tool opens and never matches on.

c

Retrieve

The agent asks for the last sixty steps as a contact sheet, then for the stair entrance near its surviving portal, then for the first frames at spawn. Each query carries the question it was for.

d

Consolidate

One patch in the same turn: a bullet in digest.md, a forensics bullet in notes.md citing the episode, and working.md rewritten as the recovery plan.

Benchmarks and arms

Minecraft (MCU)

Two long-horizon tasks scored by milestones. Mine a diamond from scratch has 10 milestones under a 12,000-step budget. Kill the Ender Dragon adds 14 more, through obsidian, the Nether, blazes and endermen, to the End.

KiCad

Twenty-four circuit design and editing tasks in one desktop application, driven by screenshots, mouse and keyboard. Rewards come from the saved schematic and netlist.

One harness, one flag

Every arm of a benchmark runs on the same harness and differs by a single flag. The engine, macro set, perception, caps, knowledge text and step budget are identical across arms.

What this does not show

  • Small n. Most cells are single runs. The skill-learning evidence is one carried chain of three lives and two fresh replicates; two fresh lives already differ by a thousand steps at the iron pickaxe.
  • One world. Every Minecraft run has the same world and spawn, so gains across lives mix map memory with procedural memory. The within-life curves are the part that does not depend on that.
  • The Nether chain is the counterexample. Runs with two, three and four carried lives all scored 16/24 and all died in the same pocket around the portal. The record carried the procedures and not the lesson that mattered.
  • MFM is not cheaper. On Minecraft it spends the most tokens of the memory arms, and on gpt-5.6-sol it trails the logbook and VISTA on the dragon task.
  • Known departures from parity. A brief longer than 32 KiB is truncated for the logbook and MFM arms on Minecraft; the KiCad direct arm is blind; the KiCad MFM cell carries extra prompt levers; scores from before and after a session-policy change are not averaged. The repository README lists them in full.
